MUSIC MASTER
COMPLETE PROJECT IMPLEMENTATION SPECIFICATION
=============================================

Product tagline:
Your Keyboard. Your Instruments. Your Music.

Document purpose:
This file is the single consolidated project brief for planning, implementing,
testing, documenting, version-controlling, packaging, and releasing Music Master.

IMPORTANT PROJECT PRINCIPLE
---------------------------
Build a real, reliable Python desktop music studio. Do not substitute fake
sounds, placeholder buttons, mock implementations, or inaccurate feature claims
for working functionality. Implement in tested milestones. The complete
instrument catalogue is the long-term scope; instrument availability depends
on properly licensed sound libraries or working synthesis implementations.

================================================================
1. PRODUCT VISION
================================================================

Music Master is a standalone desktop virtual musical instrument studio.
It transforms a laptop or desktop keyboard into a configurable musical
controller and provides instrument playback, music theory tools, MIDI support,
recording, mixing, effects, and project management.

Primary platform:
- Windows 10/11

Future platform goals:
- Linux
- macOS

Application implementation:
- Python for application logic, GUI, audio orchestration, input handling,
  persistence, music theory, recording workflows, and supporting services.
- Native dependencies used by audio libraries are allowed. A Python
  application can depend on native C/C++ audio libraries for performance.

Core objectives:
- Play instruments using laptop keyboard keys.
- Provide realistic instrument sounds.
- Support multiple simultaneous notes and instruments.
- Allow customizable keyboard mappings.
- Support multiple octaves, sustain, velocity, and transposition.
- Provide Indian and Western music theory features.
- Record and play back MIDI and audio.
- Support external MIDI controllers.
- Provide a mixer and audio effects.
- Detect optional motion sensors where hardware and OS support them.
- Work offline for core functionality.
- Save user settings and music projects locally.

Non-goals for the first milestone:
- Cloud accounts or mandatory online services.
- Social network features.
- AI music generation.
- A fake implementation of unavailable instruments.
- Loading every large sound library into memory at startup.

================================================================
4. AUDIO ENGINE ARCHITECTURE
================================================================

Recommended technologies:
- FluidSynth: SoundFont synthesis engine.
- pyFluidSynth: Python interface to FluidSynth, subject to platform compatibility.
- sounddevice: audio input/output streaming.
- NumPy: numerical and audio buffer operations.
- SciPy: digital signal processing.
- Pedalboard: audio effects.
- Mido: MIDI files and message handling.
- python-rtmidi: external MIDI input/output.
- FFmpeg or another suitable licensed encoder: optional MP3 export.

Architecture flow:

Keyboard / MIDI / UI events
          |
          v
Input and event controller
          |
          v
Note event and instrument routing
          |
          v
FluidSynth / custom synthesizer / sampler
          |
          v
Per-track mixer and effects
          |
          v
Master output and audio device
          |
          v
Speakers / headphones / audio interface

Requirements:
- Dedicated audio processing path.
- Use a dedicated audio thread or backend callback.
- Preallocate audio buffers where practical.
- Avoid blocking file, database, network, and GUI operations in audio callbacks.
- Never update Qt widgets directly from an audio callback.
- Use thread-safe queues or Qt queued signals for UI notifications.
- Support note_on and note_off.
- Support polyphony and simultaneous instruments.
- Provide panic/stop-all-notes.
- Release all active notes when focus is lost, a mapping is changed, an
  instrument is unloaded, or the application closes.
- Handle missing or disconnected audio devices.
- Support device selection.
- Support 44.1 kHz and 48 kHz where supported.
- Make buffer size configurable.
- Make polyphony configurable.
- Handle engine initialization and shutdown cleanly.
- Do not load all sound libraries at startup.
- Measure real latency on supported hardware; do not promise an unverified
  latency figure.

Initial audio buffer options to test:
- 128 frames
- 256 frames
- 512 frames
- 1024 frames

Actual latency depends on device drivers, hardware, buffer size, and operating
system. Provide a stable fallback buffer if a low-latency configuration fails.

5. KEYBOARD CONTROLLER AND DEFAULT MAPPINGS
================================================================

The keyboard controller is a signature feature.

General requirements:
- Key press triggers note_on.
- Key release triggers note_off.
- Repeated OS key events must not create duplicate active notes.
- Support simultaneous key presses.
- Support sustain.
- Support octave changes.
- Support semitone transposition.
- Support velocity configuration.
- Support custom key mapping profiles.
- Support instrument-specific mappings.
- Show visual feedback for pressed keys.
- Avoid intercepting typing in text fields.
- Handle application focus loss safely.
- Make shortcuts configurable.
- Provide a panic/stop-all-notes command.

Harmonium default concept:
A = Sa
S = Re
D = Ga
F = Ma
G = Pa
H = Dha
J = Ni
K = higher Sa

Other alphabet keys can be assigned to additional notes, accidentals,
octave extensions, or user-defined controls. The actual note mapping must
be configurable for the selected tonic and scale. Do not assume one mapping
fits every raga or tuning system.

Piano default concept:
- Number-row keys are the primary note bank.
- Alphabet keys provide additional notes, black keys, or another key bank.
- Support multiple octaves through configurable banks and octave switching.
- Make the displayed piano keyboard correspond exactly to the active mapping.

Suggested global shortcuts (all configurable):
- Ctrl+1 through Ctrl+9: select instrument/preset slots.
- Up/Down: octave change.
- Left/Right: transpose.
- Space: sustain pedal.
- R: start/stop recording when not typing in a text field.
- Esc: stop all notes.
- Ctrl+S: save project.
- Ctrl+Shift+S: save project as.

Do not hardcode shortcuts in multiple modules. Use a centralized shortcut and
mapping manager. Detect and resolve shortcut conflicts.

11. OPTIONAL MOTION SENSOR SUPPORT
================================================================

Sensor support is optional and must never be required to play instruments.

Detect hardware and OS capabilities before enabling controls. Investigate
supported Windows Sensor APIs and compatible Python bindings. On Linux,
investigate available hardware sensor interfaces.

Potential hardware:
- Accelerometer
- Gyroscope
- Magnetometer
- Orientation sensor
- Hinge-angle sensor, only if exposed by the device

Potential musical mappings:
- Tilt left/right: pitch bend
- Tilt forward/backward: filter or expression
- Orientation: modulation
- Hinge angle: expression or custom MIDI CC

Do not assume every laptop has a gyroscope, accelerometer, or hinge-angle
sensor. Provide a clear unavailable state and mouse/MIDI alternatives.
Sensor controls must be calibratable, smooth, rate-limited, and configurable.

15. GIT AND GITHUB RULES
================================================================

Branch strategy:
- main: stable, release-ready code
- develop: integration branch
- feature/*: new functionality
- fix/*: bug fixes
- refactor/*: restructuring
- docs/*: documentation
- test/*: testing improvements
- release/*: release preparation

Example branches:
    develop
    feature/audio-engine
    feature/harmonium
    feature/keyboard-mapping
    fix/audio-device-crash
    docs/update-readme

Conventional Commit format:
    <type>(<scope>): <description>

Allowed types:
- feat
- fix
- refactor
- perf
- docs
- test
- style
- build
- ci
- chore
- revert

Examples:
    feat(audio): implement FluidSynth engine
    feat(instruments): add harmonium support
    feat(input): implement keyboard mapping
    feat(theory): add raga presets
    fix(audio): resolve stuck notes on key release
    perf(audio): optimize audio buffer processing
    test(input): add keyboard mapping tests
    docs(readme): update installation instructions

Mandatory rules:
1. Commit every meaningful completed feature separately.
2. Never create one giant commit containing the entire application.
3. Never use vague messages such as update, changes, final, or working.
4. Never commit broken or untested functionality.
5. Never commit .venv, __pycache__, cache folders, temporary files, or build
   artifacts.
6. Never commit credentials, secrets, or personal settings.
7. Never commit sound libraries without redistribution permission.
8. Update tests alongside functionality.
9. Update README when installation, features, supported instruments, or usage
   changes.
10. Update CHANGELOG for notable changes.
11. Never force-push main or develop.
12. Never push directly to main; use pull requests.
13. Review git diff before committing.
14. Never describe unfinished functionality as complete.
15. Preserve existing working functionality during refactoring.

Recommended workflow:
    Implement feature
       -> Write/update tests
       -> Run quality checks
       -> Update documentation
       -> Review git diff
       -> Commit
       -> Push feature branch
       -> Create pull request
       -> Review and merge

Before committing:
    ruff check .
    ruff format --check .
    mypy src/
    pytest -q

Run relevant manual audio checks as well. Do not invent commit hashes, remote
push success, or test results. If remote credentials are unavailable, complete
local work and state that limitation.
